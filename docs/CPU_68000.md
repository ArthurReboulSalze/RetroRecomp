# Motorola 68000

The main processor of four machines: Mega Drive, Neo Geo, Capcom CPS-1 and Sharp X68000. One shared chain turns its
instructions into guarded native C, counts what it cannot translate, and is checked against a reference run on every
machine and, through the Mega Drive and CPS-1 generators, against independent vectors. This page covers the processor; each
machine's board, video and sound are on its own page.

The five measures stay separate here as everywhere ([STANDARDS.md](STANDARDS.md), rule 8): **native code** (how much of
the 68000 runs as translated C), **CPU fidelity** (agreement with a reference or with independent vectors),
**hardware fidelity**, **gameplay validation** and **physical latency**. Everything below that says "matches" is CPU
fidelity against the project's own reference or against a software corpus. It is not a statement about the original
chip, and none of it measures latency.

In each profile (`retrorecomp/systems/`) the 68000 is declared as `Cpu('m68000', 'main', 'instructions')`: its interpreted
share is counted in instructions, never added to the Z80 or any other CPU ([CPU_Z80.md](CPU_Z80.md) covers the sound
processors of three of these machines). The 68010 and later 680x0 variants are not supported; an operation of a later CPU
is an explicit limitation, not a silent extension. Machines planned on the same chain (CPS-2, Atari ST, Amiga 500) are
listed under "Reuse by CPU" in [NEW_MACHINE.md](NEW_MACHINE.md#reuse-by-cpu).

## How code is found and translated

**Common rule.** At conversion each known instruction is decoded once, and its generated C body is the pinned operation for
that mnemonic with literal operands. Execution follows the real 68000 PC and stack, including computed jumps and changed
return addresses. A covered instruction never goes through an opcode interpreter or decoder at run time. Every translated
instruction is guarded: ROM code by its position and mapping, code in RAM by a full match of all its instruction words,
so a modified routine is never run as stale native code. What is not covered runs on the counted fallback (next section).

**Paths.** What a conversion learns is stored as numbers about your own ROM, never ROM bytes
([STANDARDS.md](STANDARDS.md), rule 11). Schema 3 (`retrorecomp/path_profiles.py`) keys a game by CPU and memory map; the
68000 uses the family `m68k` with one map per machine, and these shapes:

| Shape | Kind | Row | Meaning |
|---|---|---|---|
| `phys` | `entries` | offset | an instruction start in a ROM image (even; Neo Geo also has `phys_deltas`, delta-coded roots, at most two groups) |
| `insn` | `ram_code` | address, offset, length | an instruction run from RAM, tied to the ROM bytes it came from (length 2 to 16, even) |
| `span` | `spans` | address, offset, length | a run of IPL code as a position in the player's IPL file, so no word of it is kept (X68000) |

| Machine | Map and sources | ROM code | Code run from RAM | Bounds in the profile |
|---|---|---|---|---|
| Mega Drive | `m68k/md`, `rom` | Roots from the reset and interrupt vectors; a work queue follows direct calls and jumps, both branches of conditionals (`Bcc`, `DBcc`) and fall-through, and stops after unconditional transfers (`JMP`, `BRA`, returns), at unknown indirect targets and at invalid bytes; a run of at least three equal jump stubs (`JMP d16(PC)`, `JMP abs.l`, `BRA.w`) reached once is expanded; probes add the instruction starts they miss | Learned from the demo and play probes, kept for the ROM in the converter library | entries 65,536 (even, from $200); RAM $E00000-$FFFFFF, 2,048 rows |
| Neo Geo | `m68k/ng`, `p` and `bios` | The fixed cartridge aperture (the first 1 MiB of the program ROM) and the selected BIOS are swept statically from the reset and exception vectors; banked windows use the physical roots observed in conversion plus their static successors, kept as the physical offset in the selected bank (two banks at the same virtual address stay two entries) | Observed work-RAM instructions ($100000-$10FFFF), several variants per address allowed | entries 262,144; RAM rows 4,096 |
| CPS-1 | `m68k/cps1`, `maincpu` | The whole program ROM, every even offset that decodes legally, up to 4 MiB (no `entries` are stored) | Work RAM ($FF0000-$FFFFFF), observed on one pass and translated on the next; since 1.6.4 code run from graphics RAM ($900000-$92FFFF) is guarded the same way but stays in the player's own library, never in the shared paths | RAM rows 4,096 (work RAM only) |
| X68000 | `m68k/x68`, `ipl` and `disk` | No static sweep: a fresh interpreted reference run observes what executes | Observed code in RAM, text VRAM, the SCSI IOCS ROM area ($EA0000-$EA1FFF) and the IPL, in `converter-observations.json` (private, per machine); IPL code is kept as spans over your IPL file | `insn` 65,536 rows; `span` 4,096 rows of up to 131,072 bytes |

The X68000 declares its shapes but nothing is shared yet ([X68000.md](X68000.md)); CPS-1 paths travel as an experimental
machine ([CPS1_LOG.md](CPS1_LOG.md#27-october-2026-shared-paths),
[COMPILATION_LIBRARY.md](COMPILATION_LIBRARY.md)). Imported paths are always checked again against the player's own ROM and
dropped when a conversion fails with them.

**Loop.** A conversion runs its scenarios, collects the instruction starts and RAM variants that were interpreted, generates
again and compares again, until a pass interprets nothing on the tested scenarios, stops learning, or reaches its pass
budget. The window and the report show which of these ended it.

## What stays interpreted, and why

The interpreter fallback is always counted, per CPU, in instructions, and shown: the window title says "Native code" or
"Interpreter fallback", and the conversion report ([ARCHITECTURE.md](ARCHITECTURE.md#report-schema-2)) carries the counts
per scenario beside the five measures. A fallback is never folded into a percentage of another CPU.

| Cause | Where | Effect |
|---|---|---|
| Code never seen: RAM code not yet observed, or code whose words changed since it was compiled | all four | the live words fail the guard; the instruction runs on the reference path and is counted; the next pass can compile the new variant |
| An opcode the decoder does not accept, or an operation of a later 680x0 | all four | stays a limitation; it is not reclassified as a supported illegal instruction |
| Cartridge mappings the code view does not know; instructions that would straddle protection ports or KOF '98's mutable header overlay | Neo Geo | the code stays on the reference path; protection responses are never consumed by a guard |
| Supervisor `RESET` (the pin's wiring belongs to the board) | all four, each its own way | Mega Drive: since 1.6.5 executed as a native instruction that only takes its 132 clocks (the RESET output reaches only the cartridge port on this board, where nothing here reacts; before, it halted as unimplemented); Neo Geo: not translated, so it runs on the reference path; X68000: calls the machine's reset hook; CPS-1: pin left unconnected, as in MAME, so the instruction only takes its clocks |
| Code in RAM, VRAM or the IPL whose encoding was not yet observed and guarded | X68000 | runs on the reference path inside the native build and is counted as `reference_ram` or `reference_ipl` instructions; the conversion extends the guarded code while it keeps finding new encodings |
| Address and bus errors | all four | outside the qualified scope on every machine |

Native coverage on a route says nothing about the next route: a result of zero interpreted instructions is reported "on the
tested scenarios". The per-machine tables of games and routes are in the machine pages.

## Semantics and timing

**Behaviour we model.** Synchronous exceptions enter their own vector through native code: privilege violation, illegal and
line-A/line-F opcodes, `TRAP`, `TRAPV`, `CHK`, division by zero, trace; the six-byte frame, the two stack pointers, `RTE`,
`STOP`, `MOVEP` (each byte two bus addresses apart, no flag change), `MOVEM` with its final discarded read, `CLR` and `Scc`
reading a memory destination before writing it, byte accesses through `A7` moving the stack by a word, `CMPM` post-increment
of both operands, a divide whose quotient cannot fit signalling overflow, and `MOVE.L` to a predecrement destination writing
the low word first. The details and their manual references are in
[MEGADRIVE_CPU_EXCEPTIONS.md](MEGADRIVE_CPU_EXCEPTIONS.md). The adapted text is shared: the vector replays below run it
through the Mega Drive generator, and the Neo Geo, CPS-1 and X68000 builds receive the same text through their own hooks
and are compared with Musashi. Where the manual leaves flags undefined (`CHK`, divide by zero)
a deterministic software convention is used, with no claim about the chip.

**Clocks.** The shared part is the operand-dependent cost of `MULU`/`MULS` (by operand bits) and `DIVU`/`DIVS` (by the
quotient loop), in helpers taken from the Mega Drive adapter by the other generators. The fixed costs differ by machine:

- **Mega Drive:** per-instruction clocks come from the pinned table (`interp_estimate_cycles`), corrected from the Motorola
  manual (tables 8-12 and 8-14) for status-register operations, single-operand forms, bit operations, control addressing
  modes and `MOVEM`; on top of it a two-word instruction queue shared by native and reference execution, and ordered bus
  transactions that a DMA or a Z80 bus grant can suspend ([MEGADRIVE_PREFETCH.md](MEGADRIVE_PREFETCH.md)). Since 1.6.5 a
  register-count shift or rotate (`Dx,Dy`) is charged its manual time, `6 + 2n` clocks (byte, word) or `8 + 2n` (long),
  `n` being the count modulo 64 read before the shift, through the `MULU` order (the prefetch
  read first, then the internal clocks); this is added by `megadrive_codegen.adapt_shift_timing`, not in the shared text.
- **Neo Geo, CPS-1, X68000:** the native steps charge Musashi's per-opcode table (`CYC_INSTRUCTION`) with the
  data-dependent forms computed locally (`Bcc`, `DBcc`, `Scc`, `MOVEM`, bit operations on registers, shifts by
  `(6 or 8) + 2 x count`), prefetch disabled, so native and reference sides use the same clocks; the Neo Geo schedules at
  instruction boundaries and its fine bus phases are not qualified; the Mega Drive bus and prefetch timing is not
  transplanted; the CPS-1 and X68000 compare the two sides per frame, and the X68000 adds a guest-clock and PCM ledger.

**Fixes carried as our own patches.** A fix to the shared text moves the game stamps of the four machines and rebuilds
their exports ([UPGRADES.md](UPGRADES.md)); the pin stays, so the base of qualified paths stays valid.

| Release | Fix | Where |
|---|---|---|
| 1.6.3 | `ROXL`/`ROXR` with a register count of zero (modulo 64) load C from X; `ASL.L` by 31 computes its overflow mask in 64 bits (V was wrongly set on a 32-bit shift that is undefined in C) | `m68000.adapt_semantics`; see [UPSTREAMS.md](UPSTREAMS.md#fixes-carried-as-our-own-patches-in-163) |
| 1.6.5 | Mega Drive only: the time of a register-count shift or rotate is `6 + 2n` / `8 + 2n` (long) instead of the pinned estimate for a count of four; the shift vectors are replayed with their clocks | `megadrive_codegen.adapt_shift_timing` (applied to the native bodies and to the reference path); `m68000.py` and the three other machines are untouched |
| earlier | The other adaptations listed in `adapt_semantics`: vectored `TRAP`/`CHK`/`ILLEGAL`/`RESET`, privilege checks on `MOVE to SR`, `RTE`, `STOP` and `MOVE USP`, `MOVEP`, the divide overflow boundary and zero divide, the `A7` byte rule, `CMPM`, the read before `CLR`/`Scc`, and the cycle estimates | `m68000.py`; behaviour described in the deep dives (their release is not recorded on this page) |

**Known approximations.**

- The shift and rotate clocks follow the manual's `(6 or 8) + 2 x count` on all four machines. The vectors that check
  them on the Mega Drive come from MAME, not from silicon, and cover `ROXL`, `ROXR` (byte, word, long) and `ASL.L`; the
  other register-count mnemonics (`LSL`, `LSR`, `ASR`, `ASL.B/W`, `ROL`, `ROR`) share the same line of code but have no
  independent vector of their own yet. The memory form (one bit of a word) keeps the pinned figure.
- Address and bus errors, electrical interrupt acknowledge and the external `RESET` wiring are outside the qualified scope.
- The single-step oracle does not emit the post-instruction trace delivery: that boundary is covered by authored cases only.
- On CPS-1, three sets slip by one frame against MAME during credited play because the two cores take the vertical-blank
  interrupt at slightly different instruction boundaries; a 68000 trace of one of them finds no instruction whose duration
  differs ([CPS1_LOG.md](CPS1_LOG.md#27-october-2026-credited-play-and-sound-compared-with-mame)). This is a comparison with MAME, not
  with the boards.

## Tests and vectors

Native self-tests build C and need a compiler ([BUILDING.md](BUILDING.md)); the others need neither a ROM nor a compiler.

| Check | What it covers | Run |
|---|---|---|
| `tests/test_m68000_shifts.py` | each shift adaptation applies once to the pinned text for all four hook prefixes, and a changed upstream fails loudly | unit suite (needs the cached pin) |
| `tests/fixtures/m68k-shifts` | 834 SingleStepTests vectors for `ROXL`/`ROXR` (byte, word, long) and `ASL.L`, register forms only, chosen from the inputs only; rebuilt by `tools/build_m68000_shift_fixture.py` | `tools/megadrive_prefetch_selftest.py m68k-shifts` (results, flags, queue, bus transactions and clocks) |
| `tests/fixtures/md-prefetch` | 2,089 SingleStepTests vectors plus 82 authored cases: registers, RAM, the two queue words, every ordered bus transaction and clock | `tools/megadrive_prefetch_selftest.py` |
| `tests/fixtures/md-exceptions` | 864 SingleStepTests vectors for the exception frames, saved PC, stacks and clocks, native path and reference path | `tools/megadrive_exception_selftest.py` |
| Authored Mega Drive fixtures | instruction and state comparisons, guest-stack return changes, `RTE` frames, byte stack alignment, RAM guard rejection, trace and interrupt order | `tools/megadrive_native_selftest.py`, `tools/megadrive_interrupt_selftest.py` |
| Neo Geo | ROM-free comparisons of the native ABI against Musashi, dynamic cycles, IRQ and guards, including 672 shift edge cases with X=1 (counts 0, 17, 31 and 64 for `ROXL.W`, `ROXR.W`, `ROXR.L`, `ASL.L`; 98 differed before the 1.6.3 fix); the CPU boundary itself | `tools/neogeo_m68000_selftest.py`, `tools/m68000_backend_selftest.py` |
| CPS-1 | generator, dispatch, branch targets and board tests | `tests/test_cps1_codegen.py` |
| CPS-1 vectors | the three SingleStepTests fixtures above (834 + 2,089 + 864 vectors, plus the 82 authored cases) replayed through the CPS-1 translated steps and through the same Musashi interpreting every instruction, on a flat bus; results below | `tools/cps1_vector_selftest.py` (builds C, about two minutes); `tests/test_cps1_vectors.py` (no compiler) |
| X68000 | observations, guards, device and clock vectors, kept apart from CPU agreement | `tests/test_x68000_native.py`, `tools/x68000_native_check.py`, `tools/x68000_hardware_check.py` |

The SingleStepTests corpus is MIT-licensed, generated with MAME rather than recorded from hardware, and each fixture keeps
its source hashes and licence. Its PCs include two prefetched words and are converted to architectural PCs on a flat
24-bit bus, which isolates CPU behaviour from any machine's memory map. The vector fixtures run through the Mega Drive
generator and, since 1.6.5, through the CPS-1 generator (below). Odd-address and bus errors, `TAS`, `TRAPV` and external interrupt acknowledge pins are excluded from the
prefetch and exception fixtures, which also leave out non-zero divide timings and post-instruction trace delivery.

**CPS-1 replay (29 October 2026, Windows).** The harness `native/cps1_vector_checks.c` runs each vector once through the
CPS-1 native steps (the converter's own static sweep over a flat image holding the vectors' code, run by `rr_cps1_native_run`
inside the patched Musashi loop) and once through that Musashi with every instruction interpreted. It compares registers,
SR, PC, every byte written and the clocks with the vector, and the two paths with each other. The CPS-1 clock model is
Musashi's table with prefetch disabled, not bus-accurate timing, and still equals the vectors' clocks wherever the steps agree.

- The translated steps agree with the vector on registers, SR, PC, written bytes **and clocks** for 834 of 834 shift vectors,
  2,089 of 2,089 prefetch vectors and 864 of 864 exception vectors, and for 80 of the 82 authored cases. The two others set
  the trace bit: the CPS-1 Musashi is built without trace support (`M68K_EMULATE_TRACE` off), so neither path delivers the
  post-instruction trace exception. No CPS-1 program is known to use it.
- The Musashi reference differs from the vectors where the translated steps follow them: the flags of `DIVU` and `DIVS`
  (20 and 52 vectors of the prefetch fixture, plus 5 authored cases), the flags and clocks of `CHK` (17 clock differences in
  the prefetch fixture; 5 flag and 25 clock differences in the exception fixture), and one line-F frame (the prefetch
  fixture and the exception fixture each hold it). None of the 834 shift vectors differs. The vectors come from MAME, not
  from silicon. A game that reaches one of these cases would show as a native/reference difference in the conversion's own
  comparison and be refused; the standard routes of the sets converted so far did not reach them.
- This is CPU behaviour against a MAME-made oracle on a flat bus: it says nothing about the CPS-1 board, hardware fidelity or
  gameplay. Odd-address and bus errors, `TAS`, `TRAPV` and the external interrupt pins are outside the fixtures.

**Differential checks in every conversion.** Each conversion also runs its routes twice and compares the native run with a
fresh reference that interprets every instruction: the Mega Drive's separately decoded reference path, Musashi through
Geolith on Neo Geo (the original CPU control is also replayed on the packed executable), the same board model with every
instruction interpreted on CPS-1, and a fresh reference run on the X68000. Registers, clocks, RAM, picture and sound must
match, before and after compression. That is CPU fidelity against the project's own reference, on the scenarios run.
