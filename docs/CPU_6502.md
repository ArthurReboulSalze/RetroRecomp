# 6502 (Ricoh 2A03 and 2A07)

The 6502 core of the NES processor chip, without decimal mode: every PRG ROM position is translated ahead of time to C,
code run from RAM is translated when it has been observed, and anything else goes through a counted interpreter.

The five measures are kept apart on this page as everywhere in the project: **native code** (how much of the executed
code is translated), **CPU fidelity** (does the translated CPU agree with a reference), **hardware fidelity**,
**gameplay validation** and **physical latency**. This page is mostly about the first two.

## 1. Used by

| Machine | Role of the CPU | Clock | Page |
|---|---|---|---|
| Nintendo NES, NTSC (2A03) | Main and only CPU; the same chip holds the APU and the DMA units | master clock 21.477272 MHz divided by 12, about 1.789773 MHz | [NES.md](NES.md) |
| Nintendo NES, PAL (2A07) | Main and only CPU | master clock 26.601712 MHz divided by 16, about 1.662607 MHz | [NES.md](NES.md) |

No other machine of the project has a 6502-family processor. The Dendy clock variant is not supported. The constants
are those of `native/retro_nes.h` (`RR_CPU_DIV`, `RR_MASTER_HZ`). In the machine profile the CPU is declared as
`Cpu("6502", "main", "cycles")`: the interpreter counter of this CPU is in CPU cycles, not in instructions.

## 3. How code is found and translated

**Upstream discovery.** The engine walks static control flow from the reset, NMI and IRQ vectors and from seed
entries, and it is run again with the entries a game actually reached (`--miss-log`). A banked cartridge exposes
`$8000-$FFFF` as eight 4 KiB slots that the game can remap, so the unit of compilation is a (bank, 4 KiB slot) pair,
not an address. A write that can reach a PRG bank register ends a block, and the dispatch asks the cartridge which
bank is mapped before it enters one.

**Dense coverage (ours).** The compiler prepares an entry for every physical PRG ROM byte, whatever slot a mapper
shows it in. Equal opcode and known operands share one body. A body ends after one instruction and dispatch looks at
the live bank mapping again, so a mapper write, an interrupt or a jump cannot continue in an obsolete mapping. Operands
inside the opcode's own 4 KiB bank become constants; operands across a slot boundary or wrapping from `$FFFF` are read
from the live bus. The multi-instruction blocks the engine discovered stay available next to these bodies. There is no
opcode decoder in this path; the bus cycles still go through the normal CPU, PPU and APU helpers.

**Guarded RAM bodies (ours).** An entry observed executing from RAM (internal RAM `$0000-$1FFF`, plain cartridge RAM
such as MMC5's) gets a native body selected by `(pc, opcode)`. The opcode is fetched once on the real bus and compared
with the observed one; the operands are always read from the live bus, so a changed operand needs no new variant, and
a changed opcode or an unobserved entry is interpreted. Eligibility is probed without side effects (no PPU or APU
register is read to inspect an entry). Lower ROM aliases at `$6000-$7FFF` (mappers 40 and 69) and the boards whose
bank depends on the PPU (MMC1/MMC1A, mapper 153) have their own live-fetch paths, described in [NES.md](NES.md).

**Path shape** (`retrorecomp/path_profiles.py`, schema 3, section `mos6502` of the `nes` map). Paths are numbers about
the ROM, never ROM bytes:

| Kind | Shape | Row | Meaning | Limit |
|---|---|---|---|---|
| `entries` | `nes_rows` | `(offset, pc)` | A ROM entry: `offset = bank * 0x1000 + (pc mod 0x1000)` in 4 KiB PRG banks, `pc` in `$8000-$FFFF` | 65,536 rows |
| `ram_code` | `opcode_ptr` | `(pc, offset)` | A RAM entry: `pc` in `$0000-$1FFF` or `$6000-$FFFF`, `offset` the file offset (header and trainer skipped) of a byte of the PRG area equal to the opcode | 65,536 rows |

The schema 1 equivalents are `rom_entries` and `ram_opcode_refs`. The local trace of a game (`cycle-seeds.trace`, in the
converter library `datas/library/nes`) holds lines `4k:BB:AAAA` for ROM entries and `# ram:PC:OP` for RAM entries.
An opcode can only be shared if its value occurs in the PRG of the player's own ROM, which is where it is rebuilt from,
and imported paths are checked again before use (`retrorecomp/nes_ram.py`). The guard table in the generated source is
a sorted array searched by binary search, limited to 65,536 guards. See [COMPILATION_LIBRARY.md](COMPILATION_LIBRARY.md)
for the sharing rules.

**What becomes native**: every PRG ROM position, with the cartridge's current mapping; observed RAM entries with a
guard. This does not mean that every position is code or that a game runs without interpreter use.

## 4. What stays interpreted, and why

The engine's interpreter (`cpu6502_interp.c`) runs what has no compiled body: code in RAM that was never observed (or
whose opcode changed), execution from open bus or unsupported windows, and ROM positions whose mapped bank has no
compiled body. It reads its operands at run time. It also serves as the reference of the conversion (below), so it is
never removed.

The conversion counts it in **CPU cycles**, per scenario, in three places (`retrorecomp/nes.py`, `_probe`):

| Counter | Address of the interpreted instruction |
|---|---|
| `interpreter_rom_cycles` | PRG ROM |
| `interpreter_ram_cycles` | internal RAM (`$0000-$1FFF`) |
| `interpreter_other_cycles` | Any other address: `$2000-$7FFF` that is not a modelled ROM alias (open bus, cartridge RAM code without a guard) and non-ROM windows at or above `$8000` such as MMC5 RAM |

`non_dispatch_cycles` is what remains of the total after native and interpreted cycles (reset cycles outside
instruction dispatch). The report also gives `native_cycles` and the native share. Interrupt entry (NMI, IRQ, reset,
BRK) and the jam opcodes are CPU sequences shared by native code and the interpreter, not interpreter use. The window
title, the details view and the compiled-games view show a game with interpreter use as having fallback; a result of
zero is only ever claimed for the scenarios that were run. The reporting rules are those of
[STANDARDS.md](STANDARDS.md) (rule 8).

New observations are never trusted blindly: they stay pending in the local library and become qualified when a
conversion by another player, who received them, reaches them and validates them against the reference
([COMPILATION_LIBRARY.md](COMPILATION_LIBRARY.md)); a pass that finds new RAM guards regenerates only the affected C file.
An exported game never changes its own code; it can record the fallback it meets (on by default, F12 toggles it, written
at normal shutdown), as described in [RUNTIME_FEEDBACK.md](RUNTIME_FEEDBACK.md).

## 5. Semantics and timing

- **Cycle-level bus model.** The engine models every CPU cycle as a bus access, in the order it takes for the hardware,
  including the dummy read of a page crossing and the dummy read that starts an interrupt entry. Interrupt lines are
  polled on the cycles the engine marks for it (`CYC_POLL`). The NMI input goes through an edge detector sampled every
  cycle; the IRQ line is level-sensitive and is the OR of the frame IRQ, the DMC IRQ and the cartridge IRQ (`apu_sample_irq`
  in `hw_apu.c`). These are the engine's own model, visible in `cpu6502.c`, `cpu6502.h` and `hw_apu.c` of the pinned tree.
- **DMA.** OAM and DMC transfers halt the CPU through RDY, which a 6502 honours on read cycles only (the engine's
  model; a few undocumented store opcodes look at the DMA stall on their carry cycle). On PAL our adapter suppresses the
  repeated `$4016`/`$4017` read on a DMC halt cycle unless an OAM DMA is running (`retrorecomp/nes_machine.py`, carried
  since 0.18.0, 8 October 2026); no independent PAL reference has confirmed it (last bullet).
- **No decimal mode.** The 2A03 and 2A07 have the decimal adjust disconnected. `ADC` and `SBC` are binary-only in the
  engine (`cpu_adc`, `cpu_sbc`) while `SED` and `CLD` still change the D flag. This is the behaviour of the chip and is
  not a limitation. It would be one only if a true NMOS 6502 with decimal arithmetic were added as another machine.
- **Undocumented opcodes** are part of the 256 values the self-tests cover (equality with the interpreter, not a
  correctness claim); jam opcodes freeze the CPU the way the engine models it.
- **PAL.** A CPU cycle is 16 master ticks (12 in NTSC) and a PPU dot is 5 (4 in NTSC). The interrupt-sampling ticks
  inside a CPU cycle are moved for PAL by the adapter's own scaling of the NTSC positions (NMI at tick 5 instead of 4,
  IRQ at 9 instead of 7; not measured values), and the PPU phase is kept as an integer residue modulo 5, including the
  pending cycle of a register access (`((cycles + pending) * 16 + alignment + tick) mod 5`), because 16 is not divisible
  by 5 (`retrorecomp/nes_machine.py`). Frame durations and APU periods follow the region.
- **Known approximations.** The reference run uses the same instruction templates as the native code, so a wrong
  template would be wrong in both (section 6). PAL CPU, video and audio behaviour has not been established against an
  independent source beyond the bounded checks in [NES.md](NES.md); an exploratory comparison with another emulator
  (CPU-work counters over fixed frame intervals) is not qualified because the two start at different frame phases, so
  it is not a demonstrated divergence either, and production timing is unchanged by it ([NES_LOG.md](NES_LOG.md)).
  Nothing on this page measures physical latency.

| Check | What it compares | Needs |
|---|---|---|
| `tools/nes_native_selftest.py` | Authored fixtures: all 256 opcode values across CPU slots, mapper configurations (default list: mappers 0, 1, 2, 3, 4, 5, 7, 9, 11, 26, 66, 69, 71, 78), NTSC and PAL, flag and alignment variants, page crossings, boundary operands, wrapping PC, NMI and IRQ. Native bodies against the engine's interpreter | a C compiler |
| `tools/nes_guarded_selftest.py` | Guarded RAM bodies, changed operands, rejected opcodes, PPU-driven bank changes | a C compiler |
| `tools/nes_windows_selftest.py` | Lower ROM aliases, protected cartridge RAM, DMA, pending IRQ, NMI and reset | a C compiler |
| `tools/nes_machine_selftest.py`, `nes_ppu_selftest.py`, `nes_audio_selftest.py`, `nes_state_selftest.py` | The machine around the CPU (clock, APU, PPU fast path, states); related, not CPU tests | a C compiler |
| `native/nes_dense_checks.c`, `nes_guarded_checks.c`, `nes_windows_checks.c`, `nes_machine_checks.c`, `nes_ppu_checks.c`, `nes_audio_checks.c` | The C sides of the self-tests above | built by the tools |
| `tests/test_nes.py`, `test_nes_ram.py`, `test_nes_build.py` | The converter modules: guards, traces, shared references, incremental generation | none (no ROM) |
| Conversion differential | For each scenario (boot, 120 frames by default; the input paths, 600 by default; the discovery level adds menu, select and varied-input scenarios with full budgets), per-frame state hashes and 48 kHz mono PCM of the generated run against `--interp-only` of the same executable; a difference blocks the export | the player's ROM |

Counts of cases and frames, with their dates, are recorded in [NES.md](NES.md) and [NES_LOG.md](NES_LOG.md); they are
not repeated here.

**What the evidence is.** The internal comparisons check the translation (folding of operands, dispatch, control flow,
bank mapping), because both sides share the instruction templates. There is **no independent 6502 vector set** in this
repository (the independent sets pinned by the project are for the Z80 and the 68000, [UPSTREAMS.md](UPSTREAMS.md)).
The engine ships a software oracle derived from another emulator; the project has used it for bounded private
cross-checks on NTSC cartridges, recorded in [NES.md](NES.md). The upstream README reports a hardware test ROM passing on
its own runtime; that claim is the upstream's and is not reproduced in this repository.

| Measure | What this page can say |
|---|---|
| Native code | Share of CPU cycles run by native bodies, per scenario, with the three interpreter counters shown apart |
| CPU fidelity | Native run equal to the engine's interpreter on the tested frames (state hashes, PCM); not an independent proof |
| Hardware fidelity | Not measured here; see the machine page |
| Gameplay validation | Scripted boot and input paths; no complete playthrough |
| Physical latency | Not measured |
