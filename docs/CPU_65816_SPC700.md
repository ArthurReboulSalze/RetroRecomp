# 65816 and SPC700 (Super Nintendo)

The two processors of the Super Nintendo: the 16-bit 65816 main CPU, where every ROM position has a native operation
chosen at conversion, and the SPC700 sound CPU, whose uploaded programs are translated by guarded address tables. The
cartridge coprocessors (Super FX, CX4, DSP-1) are not part of either: they are counted devices, described in section 4.

The five measures are kept apart on this page as everywhere in the project: **native code**, **CPU fidelity**,
**hardware fidelity**, **gameplay validation** and **physical latency**. The 65816, the SPC700 and each cartridge device
have their own counters and are never merged into one percentage.

## 1. Used by

| Machine | CPU | Role | Clock | Page |
|---|---|---|---|---|
| Super Nintendo | 65816 | Main CPU | Master clock 21.477272 MHz (NTSC) or 21.28137 MHz (PAL). A bus access takes 6, 8 or 12 master clocks according to the address and the FastROM setting: about 3.58, 2.68 or 1.79 MHz in NTSC | [SNES.md](SNES.md) |
| Super Nintendo | SPC700 | Sound CPU of the audio unit, with its own 64 KiB of RAM and a 64-byte boot ROM; the DSP that it drives belongs to the machine page | An oscillator independent of the video one: 1.02528 MHz on PAL; on NTSC the pinned ratio of 17,088 cycles per 357,368-clock field, about 1.0270 MHz against the NTSC master clock, not re-derived against hardware (section 5) | [SNES.md](SNES.md) |

Other machines of the project use neither processor. In the machine profile (`retrorecomp/systems/console16.py`) they
are `Cpu('65816', 'main', 'instructions')` and `Cpu('spc700', 'sound', 'instructions')`. The constants are in
`native/snes_timing.h` and `retrorecomp/snes_chips.py`; the bus access costs are those of the pinned engine
(`cpu_region_speed`).

## 3. How code is found and translated

### 65816

**No discovery for ROM.** At conversion `native_source` writes one C function for each of the 256 opcodes (the pinned
body, its cycle cost from the pinned table, the timed opcode fetch done once by the core) and a table that gives, for
every 256-byte page of the cartridge as the bus sees it, the operation of each byte. So every physical ROM byte has a
native operation. The map exists for ordinary LoROM and HiROM only (`native_source` raises for any other mapping; images
above 4 MiB and extended mappings are refused, [SNES.md](SNES.md)) and follows their mirrors; a non-power-of-two image
repeats its final block as the loader does (a 3 MiB image repeats its last MiB). Equal pages share a table. The operation
reads its operands **live** through the timed bus and takes the M and X width flags and the bank wrapping from the live
CPU state; operands are never folded into constants. The lookup
rejects a byte that differs from the compiled opcode or from the opcode returned by the real fetch, so a modified
cartridge byte or a stale preview never selects an operation.

**RAM code is learned.** Code run from WRAM or from cartridge SRAM is native only where it was observed: the table
`rr_sn_ram` holds `(pc, opcode)` pairs, looked up by binary search; the opcode must equal the live one, and operands
and widths stay live, so changed parameters need no new variant. Windows that can hold such code: WRAM (banks `$7E-$7F`
and the first 8 KiB of banks `$00-$3F`/`$80-$BF`) and the SRAM windows of the cartridge; I/O registers never. Up to
16,384 variants are kept per ROM, with overflow reported.

**Path shape** (`retrorecomp/path_profiles.py`, schema 3, section `w65c816` of the `snes` map; numbers about the ROM,
never ROM bytes):

| Kind | Shape | Row | Meaning | Limit |
|---|---|---|---|---|
| `ram_code` | `insn` | `(address, offset, length)` | A 24-bit bus address in a RAM window and where its four live bytes sit in the player's ROM (`length` is 4) | 16,384 rows |
| `ram_code` | `opcode_ptr` | `(pc, offset)` | The guard of a RAM entry: only the opcode is rebuilt, from the ROM byte at `offset` | 16,384 rows |

Schema 1: `ram_refs` and `ram_opcode_refs`. The local library keeps `datas/library/snes/<rom-sha256>/native-ram.json`;
exported games never write observations. A ROM entry needs no path: the whole ROM is covered at conversion.

### SPC700

**Uploaded sound programs.** The 65816 uploads the sound driver to the 64 KiB of APU RAM, where it is rewritten at
run time, so the SPC700 is translated by address and opcode, not by ROM position. At conversion the 256 operation bodies
are generated (the pinned bodies and cycle costs, one timed fetch each, no call to the opcode decoder), and a table maps
each of the 65,536 addresses to the set of opcodes observed there. At run time `rr_spc_native_lookup` checks the live
opcode at the program counter, side-effect free, against that set. The 64-byte boot ROM at `$FFC0` has its own mapping
and the RAM underneath it is selected only while the guest has the overlay disabled. Addresses `$F0-$FF` (volatile I/O) are never
guarded: a fetch from there takes the counted reference path. Operands and data accesses use the real APU bus.

**What the probes learn.** Conversion probes record the misses and up to four 64 KiB sound-RAM images, so the next
pass covers driver positions the run has not reached yet (the image never covers `$F0-$FF`). Observations are stored as
compressed opcode masks per address in `datas/library/snes/<rom-sha256>/spc-native.json` (bounded, tied to the ROM).

**Path shape** (section `spc700` of the `snes` map; windows exclude `$F0-$FF`; at most 262,144 decoded positions per
game): all rows say that at an APU address the opcode equals the ROM byte at `offset`, because that is where the driver
comes from.

| Shape | Row | Meaning |
|---|---|---|
| `spc_refs` | `(pc, offset)` | One address |
| `spc_ranges` | `(first, last, offset)` | Consecutive addresses with the same opcode source |
| `spc_bitmaps` | `(first, mask, offset)` | 32 addresses from a multiple of 32, by bit |
| `spc_deltas` | `(offset, [deltas])` | Address gaps; the converter keeps the smaller of bitmaps and deltas per record |

All four are `ram_code` rows, losslessly interchangeable; schema 1 has the fields `spc_refs`, `spc_ranges`,
`spc_bitmaps` and `spc_deltas`. See [COMPILATION_LIBRARY.md](COMPILATION_LIBRARY.md) for sharing and requalification.

**Learning runs.** The SNES conversion scenarios are the attract demo and play at every scan level; from *Extended* up,
longer attract runs, reproducible pseudo-random play routes seeded by the ROM's own hash and, for the six Super FX cartridges
that have one (Star Fox, Star Fox 2, Stunt Race FX, Yoshi's Island, Vortex, Dirt Racer), an authored route
([SNES.md](SNES.md#converting-and-the-scan-levels); the varied-input replays are Mega Drive only). Each scenario is
compared with the internal reference before new RAM variants or SPC700 opcodes enter the local library.

## 4. What stays interpreted, and why

| Where | What is interpreted | Counted as |
|---|---|---|
| 65816 | RAM or SRAM code not observed, or whose opcode changed; a ROM byte changed after conversion; code run from a window that cannot be guarded | `interpreted_opcodes` (`main_interpreted_opcodes`), `native_entries`, `native_percentage` (in opcodes): 65816 only |
| SPC700 | Unobserved driver code, a changed opcode, a fetch from `$F0-$FF` | `audio_interpreted_opcodes` and `audio_interpreted_cycles`, `audio_native_percentage` (in cycles); ticks where the stopped CPU only advances the clock are `spc_idle_cycles`, apart from retired opcodes |

These are the flat report keys; the same figures are written per CPU in the schema-2 sections `cpus[]` and `devices[]`
([ARCHITECTURE.md](ARCHITECTURE.md#report-schema-2)), which will remain when the flat keys are dropped.
| Super FX (GSU-1, GSU-2) | **Every GSU instruction.** The GSU runs on the engine's instruction core (semantics adapted upstream from the ares implementation) | The `cartridge_device` entry: chip `superfx`, mode `interpreted`, unit "device instructions", per scenario and per frame |
| CX4 | Every device instruction, on the engine's instruction core with synthesized constants | `cartridge_device`: chip `cx4`, mode `interpreted` |
| DSP-1 | Not an instruction interpreter: a firmware-free command model (firmware-dump commands are a validation error; no firmware is involved) | `cartridge_device`: chip `dsp1`, mode `command_model` |

Any other enhancement circuit (SA-1, S-DD1, SPC7110, DSP-2/3/4, other custom chips) is refused with an explicit message
and is not converted. No firmware is loaded, shipped or looked for in the working directory.

**Why the device is separate.** A Super FX game executes tens of millions of GSU instructions per scenario; in one
percentage they would swamp the 65816 and SPC700 and say nothing about either. The three figures are therefore shown
apart in the report, the details view, the window title ("Cartridge chip interpreted" when only the device is
interpreted), the compiled-games view and problem reports. **No zero-fallback claim is made for a Super FX or CX4
game.** The 65816 percentage never includes device instructions, and a native 65816 or SPC700 path never hides
interpreted device work.

**The GSU stays interpreted.** Static recompilation of GSU programs was studied: a prefix-aware decoder
(`retrorecomp/snes_gsu.py`) and a survey tool (`tools/snes_gsu_survey.py`) exist and are not used by the conversion
path. The GSU core measured at 7-27 % of host frame time, so recompiling it would buy little speed; the remaining work
(learning records, an emitter with cycle accounting that matches the interpreter, guards, a per-job checker) was set aside on 27 October 2026
and the plan stays recorded in [SNES_SUPERFX.md](SNES_SUPERFX.md). The 7-27 % is a sampling profile of the local Super FX
cartridges on one host, not a pinned measurement and not a latency figure. The same page holds the Super FX board list, memory
map and the timing comparison with another emulator.

## 5. Semantics and timing

- **Modes and widths.** Emulation and native modes, the 8 or 16-bit accumulator and index widths, decimal arithmetic,
  bank wrapping and the data bus latch are those of the pinned core. The native operations read their widths live.
- **Bus chronology** (machine side, in `native/snes_bus.inc`). CPU reads and writes are priced as they happen:
  a read samples after its 6, 8 or 12-clock cycle minus the last four clocks, a write reaches the device at the end of
  its cycle, MMIO words are two ordered byte transfers, and host code-inspection reads (guards, lookahead) take no guest
  time. DMA and HDMA wait for the next CPU bus edge, take the bus on an eight-clock divider and release it on the next
  CPU cycle. DRAM refresh holds the beam for 40 clocks per line. Internal (unused) cycles of an instruction are still
  charged at retirement: **their position inside each addressing mode, and the parked-CPU handshake, are not
  qualified.** The details are in [SNES.md](SNES.md).
- **Interrupts.** The beam frame driver takes hardware NMI and IRQ with `rr_snes_cpu_interrupt`: timed dummy, stack and
  vector accesses, the bank stacked only in native mode (7 cycles in emulation mode, 8 in native), I set and D cleared,
  and the vector chosen by the mode (`$FFFA/$FFFE` in emulation mode, `$FFEA/$FFEE` in native). `native/snes_bus_checks.c`
  checks both modes. The scheduler yields at the field deadline or at `WAI`, keeps the architectural stack across a
  field, lets a raster IRQ preempt an NMI handler that executed `CLI`, and publishes the address `RTI` actually pops (a
  game can switch tasks that way). The upstream function `interp816_doInterrupt` (bank always stacked, native vectors) is
  not on this path: the pinned tree reaches it only through flags set by its SA-1 core, and SA-1 cartridges are refused.
- **Fix carried as our own patch (1.6.3, 65816).** `BRK` in native mode takes 8 cycles (the program bank is stacked) and 7
  in emulation mode; `COP` follows the mode (in emulation mode no bank is stacked, 7 cycles, vector `$FFF4`). Written from
  the processor manual; one corrected source feeds both the compiled operations and the interpreter copy of the project
  (`snes_codegen.correct_software_interrupts`, `read_core`). The `snes` game stamp moves, so SNES exports of 1.6.2 are
  converted in full. It is a CPU fidelity fix only ([UPSTREAMS.md](UPSTREAMS.md#fixes-carried-as-our-own-patches-in-163),
  [UPGRADES.md](UPGRADES.md#cpu-fixes-carried-from-the-upstream-review-in-163)).
- **Sound timing.** The SPC700 runs from its own oscillator. PAL maps the master clock to 1.02528 MHz with fractions
  carried between iterations. NTSC keeps the pinned engine's nominal ratio (17,088 APU cycles per 357,368 master clocks
  of a field), inherited unchanged and not re-derived against hardware. Instruction costs,
  taken-branch penalties, stopping, timers, DSP access and the CPU/APU port scheduling are kept.
- **Reset.** Resetting the machine clears the architectural CPU state and clocks, and the FastROM (MEMSEL) shadow, which
  otherwise survived a restart and changed early boot timing.
- **Known approximations.** Instruction-internal cycle placement and parked-CPU phases (above); DMA and HDMA launch and
  release phases at the finest level; the NTSC audio ratio; the open OAM-address disagreement between two reference
  emulators (a PPU matter, recorded in [SNES.md](SNES.md)). None of these is reported as independently established.

Counts of cases, frames and cartridges, with dates, are in [SNES.md](SNES.md) and [SNES_LOG.md](SNES_LOG.md); they are
not repeated here.

**What the evidence is.** Apart from the authored-value assertions listed above (BRK and COP against the manual, the
SPC700 timing assertions, the audio-clock fixtures), the 65816 and SPC700 self-tests and the conversion comparison are
against the pinned core's own interpreter, which shares its bus and devices with the native path: they find divergence
introduced by translation and are explicitly not independent hardware proof (the check sources say so). There is **no independent 65816 or SPC700
vector set** in this repository; the independent vector sets pinned by the project are for the Z80 and the 68000
([UPSTREAMS.md](UPSTREAMS.md)). Independent evidence on this machine exists for hardware behaviours and chip maths
(authored guest programs compared with other emulators, and a GSU model written from public documentation) and is
described on the machine pages.

| Measure | What this page can say |
|---|---|
| Native code | 65816 and SPC700 reported apart, in opcodes (and cycles for the SPC700); device instructions on their own line; "zero" only for the scenarios run |
| CPU fidelity | Native equal to the pinned interpreter on tested routes; the BRK/COP fix checked against the manual |
| Hardware fidelity | Not claimed for the CPUs; finer bus phases and cartridge circuits are open work |
| Gameplay validation | Scripted routes and sampled gameplay, not completed games |
| Physical latency | Not measured |
