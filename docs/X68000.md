# Sharp X68000 — experimental development

The X68000 prototype is progressing quickly, using the shared 68000 work from
Mega Drive and Neo Geo. It has produced local standalone games on Windows and
Debian, with guarded native execution of code loaded into RAM.

Current work includes DIM/XDF disks and M3U sets, shared controls and display
options, F8/F9 states, keyboard/gamepad autofire, and automatic disk changes.
Since 1.6.3 the window, menus, controls pages and sound output are those of the
host kit ([HOST_KIT.md](HOST_KIT.md)), shared with the other consoles; the guest
keyboard, the mouse, the disks and fast loading stay the X68000's own.
The defaults are W/X for buttons A/B. F1 and F2 open and close
their menus; Shift+F1 restarts at once, as on every console. An option on the
last F2 page hands F1–F10 to the X68000; Ctrl+F1–F12 then reach Retro-Recomp
(see [computer function keys](CONTROLS.md#computer-function-keys-x68000)). More games, disk sequences, hardware cases and low-power Linux
performance still need qualification.

Nineteen game sets are converted on Windows and Debian with the current
machine runtime. Each native export matches a fresh reference run (CPU, memory,
picture, PCM and clock traces) on a 4,000-frame route plus mouse and keyboard
routes, and resumes identically after a saved state. No fallback was observed on
those sampled paths, and the campaign traces match between Windows and Debian. This does not establish complete gameplay coverage or exact hardware
fidelity. The other console profiles retain their documented scope.

## Automatic disk changes

Every game made from two or more disks answers its own disk requests; no list
of known games is involved. A request is a drive the game ejected and then
keeps polling (in at least two frames after the eject), or an empty drive whose
light it blinks. After a short removal interval (16 frames), the next disks of
the ordered set are offered in turn; after an eject, the disk in the other drive
may be moved over. A disk the game ejects again within 300 frames is treated as
refused: a moved disk returns to its drive and the next one is offered. When
every disk is refused, the drive stays empty and the manual disk keys remain
available. Games that eject disks once everything is loaded, and stop looking at
the drives, are left alone. Pending requests are part of F8/F9 states.
Conversion reports list each route's disk events (guest ejects and polls,
blinks, automatic insertions) next to the number of automatic changes.

Measured on bounded routes: Metal Sight changes disks at the same frames as its
former hand-written rules; Power Unit finds its third disk after one refusal;
Choujin and Super Hang-On, which eject their disks after loading, run exactly as
without the policy. Disk requests deeper in a game than the conversion routes
reach have not been observed.

## Multi-disk sets

Adding a folder, or a single disk of a set, queues each multi-disk game once.
Disks of one folder that share a name apart from their disk tag
(`(Disk 1 of 3)`, `(Disk 2)`, `(Disk C)`, with any `(System)`, `(User)` or
`(Data)` label after it) are ordered by number and written as an M3U playlist
under `datas/x68000-sets`; nothing is written beside the disks, and the
playlist gives the game the same identity as an equivalent hand-written M3U.
Alternate dumps marked `[a]`, `[a2]` form their own sets. A disk named by your
own M3U stays inside it. Names that repeat a disk number or disagree on the
number of disks are left as separate files, and a set with a missing disk is
queued with the disks found and reported in the log. On the test collection
(418 DIM files), this gives 33 sets; the 12 multi-disk sets qualified earlier
from hand-written playlists are found with the same identity.

## Game and machine identity

A game is its ordered disk set (a single disk and a one-disk playlist are the same
game). That key names the report's `rom.sha256`, the collection, the library entry
(`library/x68/<game>/`, with the observations of each machine beneath it) and the
gameplay feedback file of the exported player. The **machine** (disks + your IPL + font
ROM + RAM size) is a second, finer identity: it names the saved data, the quick states
and the converter's observations, because they depend on the firmware. Observations
and summaries written by 1.5 and earlier outside the library are copied in, never
deleted; see [the library note](COMPILATION_LIBRARY.md#x68000-one-game-key-observations-in-the-library-standardization-6a-27-october-2026-part-of-the-160-stamp-break).

## What the converter remembers of the IPL

The conversion's memory of a machine (`converter-observations.json`, private, one per machine) lists where
instructions were seen to start. For the IPL window it stores positions in your IPL, never IPL words: an entry is
`[position, length in words]` in a span over your IPL file, and the words are read back from your IPL when the
file is used (see [the library note](COMPILATION_LIBRARY.md#x68000-one-game-key-observations-in-the-library-standardization-6a-27-october-2026-part-of-the-160-stamp-break)).
Observations written by earlier versions are still read and are rewritten in this form by the next conversion of
the machine. Code in RAM and text VRAM is still kept as words. Nothing of this is shared: the X68000 remains
local and experimental.

## Mouse games

A mouse game is captured at launch (Ctrl+Alt+M releases it), and the keyboard
or gamepad can also move the pointer and press its buttons. In other games a
click in the window still captures the mouse.

The 84 sets of the test collection that read the mouse are listed in
`native/x68000_reference/mouse_games.json`, by exact disk-set identity: 70 with
mouse controls, 14 without. Each set ran the 4,000-frame main route and the
10,000-frame mouse route on the interpreted reference; a mouse read is an
executed IOCS `_MS_GETDT`, `_MS_CURGT`, `_MS_OFFTM` or `_MS_ONTM` call, or RAM
code driving the mouse's SCC channel B ($E98000–$E98003) itself, as Lemmings,
Populous and Cameltry do. A game listed with mouse controls reads the mouse at
least 1,000 times on the mouse route, and its picture differs, when that route
is replayed without the mouse, on at least half the following frames; the
other 14 read the mouse less, or without such a reaction. The list was
reviewed before inclusion.

Any other set is observed during its conversion: loaded code that reads the
mouse lengthens the mouse route, and 1,000 reads executed on fresh routes turn
the mouse controls on. The decision is kept per exact set for later quick
conversions and recorded in the report (`mouse_controls`). Mouse use deeper in
a game than these routes reach is not observed.

## Availability

The X68000 profile is included in the converter as an **experimental** profile.
Add DIM/XDF disks or an ordered M3U set, and select your own IPL ROM and font
ROM (CGROM) in **Options → Sharp X68000**. Disks named as one set, such as
`Game (Disk 1 of 2).dim`, `Game (Disk 2).dim` or `Game (Disk B).dim`, are
queued as a single game (see [multi-disk sets](#multi-disk-sets)). On the first conversion the converter
fetches hissorii/px68k, Geolith and GenesisRecomp at their pinned revisions,
like the other profiles' dependencies. No firmware, disk, generated game or
private instruction observation is distributed.

The machine runtime contains no file of the GPL-declared libretro fork. It is
built from hissorii/px68k (2014) under Kenjo's noncommercial terms, NONAKA
Kimihiro's BSD files and cisc's FMGEN terms, with Musashi (MIT) and
Retro-Recomp's own MIT host glue and snapshots. hissorii's port is used on the
same noncommercial terms as the rest of the Kenjo lineage, as PX68k has been
distributed since 2013. Notices: [machine runtime](../licenses/x68000-machine.md),
[FMGEN](../licenses/fmgen.md), [Musashi](../licenses/musashi.md).

What is measured, kept separate: native code (each export matches a fresh
reference run on bounded joystick, mouse and keyboard routes, with the fallback
interpreter count reported), CPU and hardware checks (authored video, audio,
timing, session and disk vectors and 20 CPU guards), and continuation after a
saved state. Complete gameplay, exact hardware fidelity and physical latency are
not established by these checks.

Since 1.5.0, Linux exports are compressed with the bundled UPX after their
validation, like the other consoles and like X68000 games on Windows. The
player takes its disks, IPL and font ROM from its own memory, never by reading
its file, so UPX restores them with the program. Sizes, start-up times and
quick states between the uncompressed and compressed builds are in
[BUILDING.md](BUILDING.md#linux-game-compression).

## Projects used by the prototype

- [PX68k by hissorii](https://github.com/hissorii/px68k), revision
  `74ddbb37b4e12b77362a4e12f28ceb5aaa593684`: machine devices from Kenjo's
  WinX68k/Keropi, NONAKA Kimihiro's xkeropi and hissorii's port, with cisc's
  FMGEN for the YM2151.
- [Geolith / libretro](https://github.com/libretro/geolith-libretro), revision
  `2dc88e3fa72ff404213a65d6eb5bb33baa687f73`: the Musashi CPU baseline reused
  with X68000 callbacks.
- [GenesisRecomp](https://github.com/mstan/segagenesisrecomp) and
  [m68k-recomp-core](https://github.com/mstan/m68k-recomp-core): shared 68000
  decoding and native instruction work.
- [PX68k / libretro](https://github.com/libretro/px68k-libretro) served as the
  earlier development reference; none of its files is compiled any more.

The application credits link to these repositories. Their individual terms
remain applicable; the RetroRecomp MIT notice does not relicense them.

## What comes next

Continue hardware and gameplay qualification, improve the machine-runtime
distribution boundary, and extend multi-disk coverage. More consoles and
classic computers are planned. Each new machine will have its own experimental
stage and validation before being described as supported; no release dates or
complete compatibility are promised.

## Scan levels

**Options → Sharp X68000 → Discovery scan** chooses the exploration routes
replayed beside the 4,000-frame main route, each compared with a fresh
reference. *Quick* keeps the main route only; *Standard*, the default, adds the
mouse and keyboard exploration; *Extended* adds one 18,000-frame pseudo-random
route; *Thorough* replays the three 36,000-frame routes that qualified the
library. Routes replay side by side within the game's share of the host CPUs,
which cut a thorough conversion from about 21 to about 9 minutes on the test
machine. The report records `scan_level`.
