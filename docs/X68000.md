# Sharp X68000

Experimental profile (`x68`): Sharp X68000 floppy games (DIM and XDF disks, ordered sets and M3U playlists), converted
into standalone Windows or Linux executables with guarded native code for the 68000 code the game loads into RAM, and
a counted interpreter for everything else. Your own IPL ROM and font ROM (CGROM) are needed; nothing of the machine is
distributed.

## 1. At a glance

| | |
|---|---|
| Status | **Experimental**: Options → Sharp X68000, profile `x68`, 4,000-frame main route |
| Converted | Floppy games: `.dim` and `.xdf` disk images, `.m3u` playlists, and the disks of one game queued as a single set |
| Processor | One Motorola 68000, main CPU ([CPU_68000.md](CPU_68000.md)) |
| Firmware needed | Your own **IPL ROM** (128 KiB) and **font ROM** (CGROM, 768 KiB), chosen in Options → Sharp X68000 (`--x68-ipl`, `--x68-cgrom` on the command line). RAM size is an option: 2 or 4 MiB (default 2) |
| Exports | `Games/Sharp X68000` beside the converter. The disks, IPL and font ROM are embedded in the executable and taken from its own memory, never by reading its file |
| Reports | Common report v2; the result line counts interpreted 68000 opcodes like the other opcode consoles |
| Not distributed | No firmware, disk, generated game or private instruction observation |

What is measured, kept separate (details in [Qualification](#7-qualification)): **native code** (how much of the
executed 68000 code runs as guarded native code, interpreter count reported), **CPU fidelity** (each export is compared
with a fresh reference run on bounded routes), **hardware fidelity** (authored video, audio, timing, session and disk
vectors, plus 20 CPU guards), **gameplay validation** and **physical latency**. Complete gameplay, exact hardware
fidelity and physical latency are not established by these checks.

### Game and machine identity

A game is its ordered disk set (a single disk and a one-disk playlist are the same game). That key names the
report's `rom.sha256`, the collection, the library entry (`library/x68/<game>/`, with the observations of each machine
beneath it) and the gameplay feedback file of the exported player. The **machine** (disks + your IPL + font ROM + RAM
size) is a second, finer identity: it names the saved data, the quick states and the converter's observations, because
they depend on the firmware. Observations and summaries written by 1.5 and earlier outside the library are copied in,
never deleted; see [the library note](COMPILATION_LIBRARY.md#x68000-one-game-key-observations-in-the-library-standardization-6a-27-october-2026-part-of-the-160-stamp-break).

### Multi-disk sets

Adding a folder, or a single disk of a set, queues each multi-disk game once. Disks of one folder that share a name
apart from their disk tag (`(Disk 1 of 3)`, `(Disk 2)`, `(Disk C)`, with any `(System)`, `(User)` or `(Data)` label
after it) are ordered by number and written as an M3U playlist under `datas/x68000-sets`; nothing is written beside the
disks, and the playlist gives the game the same identity as an equivalent hand-written M3U. Alternate dumps marked
`[a]`, `[a2]` form their own sets. A disk named by your own M3U stays inside it. Names that repeat a disk number,
disagree on the number of disks, or exceed ten disks are left as separate files, and a set with a missing disk is
queued with the disks found and reported in the log. On the test collection (418 DIM files), this gives 33 sets; the 12
multi-disk sets qualified earlier from hand-written playlists are found with the same identity.
(`retrorecomp/rom_sources.py`, `disk_sets`.)

## 2. Structure of the machine

| Part | In the machine | How Retro-Recomp handles it |
|---|---|---|
| Main CPU | Motorola 68000 ([CPU_68000.md](CPU_68000.md)) | Musashi (from Geolith) is the **reference** and the counted interpreter. Native code is generated only for encodings seen executing in RAM, text VRAM, the SCSI ROM area or the IPL, each guarded by a live check of its instruction words |
| Memory | 2 or 4 MiB main RAM (12 MiB ceiling of the address map), IPL ROM, font ROM, SRAM, text and graphic VRAM | Reference machine from the pinned px68k base; the IPL and font ROM are yours, hashed into the machine identity |
| Video | CRTC, graphic and text VRAM, BG/sprites, palette, line composition | Reference machine (px68k devices and `windraw` line composition); the picture size varies, up to 800 × 600, shown by the host kit with 4:3 aspect |
| Sound | YM2151 (OPM, FMGEN), ADPCM, MIDI port | Reference machine; the sound comes out at 44.1 kHz through the host kit |
| DMA, interrupts, timers | DMAC, MFP, IOC, IRQ handling, system port, RTC | Reference machine; clocks are integer guest counts (`hardware_clock.c`), never wall-clock |
| Floppy | FDC and two drives (FDD0 and FDD1), DIM / XDF images | Reference machine plus the media session (automatic disk changes, [below](#automatic-disk-changes)) |
| Input | Keyboard (MFP), mouse (SCC channel B), joystick (PIA) | Pads and keys feed the joystick; the guest keyboard and the captured mouse stay the computer's own ([Controls](#5-controls-and-options)) |
| Storage | SASI and SCSI controller code | Present in the pinned base; the profile accepts floppy media only (`media_kinds = ('disk',)`) |

### Native code and the interpreter

A conversion runs the game on the fresh reference (every instruction interpreted), observes where instructions started,
generates native code for those encodings, builds the player and compares it with the reference. If interpreted
opcodes remain, up to three passes (the default; `passes`) extend the guarded coverage; whatever is still interpreted stays counted and shown
per CPU and per device. Each guarded entry checks the live instruction words, so code that changes in RAM falls back
to the interpreter instead of running stale. The path profile of the machine (`retrorecomp/path_profiles.py`, section
`m68k`/`x68`) keeps positions in the IPL and the disks, never bytes; its address windows are the RAM, text VRAM, SCSI ROM
area and IPL ranges.

**What the converter remembers of the IPL.** The conversion's memory of a machine (`converter-observations.json`,
private, one per machine) lists where instructions were seen to start. For the IPL window it stores positions in your
IPL, never IPL words: an entry is `[position, length in words]` in a span over your IPL file, and the words are read
back from your IPL when the file is used (see [the library note](COMPILATION_LIBRARY.md#x68000-one-game-key-observations-in-the-library-standardization-6a-27-october-2026-part-of-the-160-stamp-break)).
Observations written by earlier versions are still read and are rewritten in this form by the next conversion of the
machine. Code in RAM and text VRAM is still kept as words. Nothing of this is shared: the X68000 remains local and
experimental.

## 3. Engine and upstream

The machine runtime contains no file of the GPL-declared libretro fork. It is built from hissorii/px68k (2014) under
Kenjo's noncommercial terms, NONAKA Kimihiro's BSD files and cisc's FMGEN terms, with Musashi (MIT) and Retro-Recomp's
own MIT host glue and snapshots. hissorii's port is used on the same noncommercial terms as the rest of the Kenjo
lineage, as PX68k has been distributed since 2013. Notices: [machine runtime](../licenses/x68000-machine.md),
[FMGEN](../licenses/fmgen.md), [Musashi](../licenses/musashi.md). The generated native 68000 code builds on
GenesisRecomp / m68k-recomp-core (PolyForm Noncommercial, see [its notice](../licenses/segagenesisrecomp.md)); the
pins, review record and deferred fixes are in [UPSTREAMS.md](UPSTREAMS.md).

On the first conversion the converter fetches hissorii/px68k, Geolith and GenesisRecomp at their pinned revisions, like
the other profiles' dependencies.

The application credits link to these repositories. Their individual terms remain applicable; the RetroRecomp MIT
notice does not relicense them.

The 68000 translation is the work shared with the Mega Drive, Neo Geo and CPS-1 (`m68000.py`, owned by the lead).

Our own code on top: the MIT host glue and state snapshots (`native/x68000_machine/`, written from a behavioural
specification, with a manifest of what may be kept, `provenance.json`) and the reference host. Of three px68k-libretro
fixes, two are carried as patches of the machine base since 1.6.5 (a DMA start on a busy channel restarts it; a moved
sprite marks the lines it covers for redraw) and one is not adopted (UPSTREAMS.md, "Deferred"); each was checked against
our base and rewritten from its description, never from the GPL code. The 68000 fixes carried as our own patches are listed in [CPU_68000.md](CPU_68000.md).

## 5. Controls and options

The window, menus, controls pages and sound output are those of the host kit ([HOST_KIT.md](HOST_KIT.md)), shared with
the other consoles since 1.6.3 ([CONTROLS.md](CONTROLS.md)); the guest keyboard, the mouse, the disks and fast loading
stay the X68000's own.

- **Game buttons.** Defaults: W and X for buttons A and B, Enter for Start, arrows for directions, Pause unbound.
  F1 and F2 open and close their menus; Shift+F1 restarts at once, as on every console. F6 toggles autofire on the
  two game buttons, F8/F9 save and load a quick state.
- **Computer function keys.** An option on the last F2 page hands F1-F10 to the X68000; Ctrl+F1-F12 then reach
  Retro-Recomp (see [computer function keys](CONTROLS.md#computer-function-keys-x68000)).
- **Ctrl+Alt chords** (second help page, Tab in F1): K full guest keyboard (then F2-F10 go to the computer), M mouse
  capture, F autofire, Page Up/Down change the disk in FDD0 (add Shift for FDD1), Backspace ejects, H help, O options,
  Enter display mode, Q quit. F5 (held) is fast loading, unthrottled and silent; any input interrupts an automatic
  fast loading. F11 pauses.
- **Display and sound.** Picture size follows the machine (up to 800 × 600), shown through the host kit's display
  options; sound is stereo 44.1 kHz.

### Mouse games

A mouse game is captured at launch (Ctrl+Alt+M releases it), and the keyboard or gamepad can also move the pointer and
press its buttons. In other games a click in the window still captures the mouse.

The 84 sets of the test collection that read the mouse are listed in `native/x68000_reference/mouse_games.json`, by
exact disk-set identity: 70 with mouse controls, 14 without. Each set ran the 4,000-frame main route and the
10,000-frame mouse route on the interpreted reference; a mouse read is an executed IOCS `_MS_GETDT`, `_MS_CURGT`,
`_MS_OFFTM` or `_MS_ONTM` call, or RAM code driving the mouse's SCC channel B ($E98000–$E98003) itself, as Lemmings,
Populous and Cameltry do. A game listed with mouse controls reads the mouse at least 1,000 times on the mouse route,
and its picture differs, when that route is replayed without the mouse, on at least half the following frames; the
other 14 read the mouse less, or without such a reaction. The list was reviewed before inclusion.

Any other set is observed during its conversion: loaded code that reads the mouse lengthens the mouse route, and 1,000
reads executed on fresh routes turn the mouse controls on. The decision is kept per exact set for later quick
conversions and recorded in the report (`mouse_controls`). Mouse use deeper in a game than these routes reach is not
observed.

### Automatic disk changes

Every game made from two or more disks answers its own disk requests; no list of known games is involved. A request is
a drive the game ejected and then keeps polling (in at least two frames after the eject), or an empty drive whose light
it blinks. After a short removal interval (16 frames), the next disks of the ordered set are offered in turn; after an
eject, the disk in the other drive may be moved over. A disk the game ejects again within 300 frames is treated as
refused: a moved disk returns to its drive and the next one is offered. When every disk is refused, the drive stays
empty and the manual disk keys remain available. Games that eject disks once everything is loaded, and stop looking at
the drives, are left alone. Pending requests are part of F8/F9 states. Conversion reports list each route's disk events
(guest ejects and polls, blinks, automatic insertions) next to the number of automatic changes. The policy lives in
`native/x68000_reference/media_session.c` (`RR_MEDIA_INSERT_WAIT` 16, `RR_MEDIA_REJECT_WINDOW` 300).

Measured on bounded routes: Metal Sight changes disks at the same frames as its former hand-written rules; Power Unit
finds its third disk after one refusal; Choujin and Super Hang-On, which eject their disks after loading, run as
without the policy. Disk requests deeper in a game than the conversion routes reach have not been observed.

### Scan levels

**Options → Sharp X68000 → Discovery scan** chooses the exploration routes replayed beside the 4,000-frame main route,
each compared with a fresh reference. *Quick* keeps the main route only; *Standard*, the default, adds the mouse and
keyboard exploration; *Extended* adds one 18,000-frame pseudo-random route; *Thorough* replays the three 36,000-frame
routes that qualified the library. Routes replay side by side within the game's share of the host CPUs, which cut a
thorough conversion from about 21 to about 9 minutes on the test machine. The report records `scan_level`.

## 6. States and saves

F8 and F9 save and load a quick state of the whole machine, including pending disk requests; a state loads in a fresh
process and the continuation is part of every conversion (a state taken near the end of the main route, and one taken
at frame 120 to cover an early floppy DMA, are each resumed and compared with the saved timeline).

- **Deterministic since 1.6.3.** Every byte of a quick state is a value of the machine; the FM chip is allocated
  zeroed ([GAME_STATES.md](GAME_STATES.md), [UPGRADES.md](UPGRADES.md#x68000-exports-in-163-host-kit-phase-3)).
- **Between releases:** quick states are refused (the key carries the compiler's identity by design); compatibility is
  not promised. The X68000 is never in `LEGACY_GAME_STAMPS`: an export of a previous release is converted in full once.
- **Saved data and states** are named by the machine identity (disks + IPL + font ROM + RAM), because they depend on
  the firmware; they live under `datas/games/x68-<identity>`.
- **The game's writable disks** are the X68000's ordinary saves: each disk of the set is copied from the executable into
  `datas/games/x68-<identity>/media` on the first start and then belongs to the player. Every later start, and a
  reconversion of the same disks, IPL, font ROM and RAM size (which has the same identity, so finds the same folder),
  keeps the played disk as it is. A floppy image keeps its size whatever the game writes, so a disk of another size, a
  folder in its place or a missing file is not this disk: it is moved to `<name>.unusable-1` (then `-2`, up to `-99`),
  never deleted, and the original is written again from the executable. A host file that was changed (the playlist, the
  IPL or the font ROM copy) is treated the same way. The start is refused only for a link or a hard link in place of a
  file, or when another copy of the same game is running. The machine keeps no battery memory outside states.
- **Linux exports** are compressed with the bundled UPX after their validation (since 1.5.0), like the other consoles
  and like X68000 games on Windows; sizes, start-up times and states between the uncompressed and compressed builds are
  in [BUILDING.md](BUILDING.md#linux-game-compression).

## 7. Qualification

Gate-by-gate status is in [QUALIFICATION.md](QUALIFICATION.md) (column `x68`); what "supported" requires is in
[STANDARDS.md](STANDARDS.md#supported-checklist). The X68000 stays **experimental**: the other console profiles retain
their documented scope.

- **Nineteen game sets** are converted on Windows and Debian with the current machine runtime. Each native export
  matches a fresh reference run (CPU, memory, picture, PCM and clock traces) on a 4,000-frame route plus mouse and
  keyboard routes, and resumes identically after a saved state. No fallback was observed on those sampled paths, and
  the campaign traces match between Windows and Debian. This does not establish complete gameplay coverage or exact
  hardware fidelity.
- **Per conversion**, the pipeline refuses to replace an existing export unless the standalone player's trace matches
  the fresh reference on the main route and on every exploration route of the scan level, the compressed copy of that
  player (compressed as it is published) matches the same reference on the same routes, the state continuation of that
  compressed copy matches (F8/F9 in a fresh process and the early floppy DMA), and the picture is not empty and changes
  on the main route. A main route with no sound at all is accepted and reported (`native_validation.sound_heard` false,
  and a line in the conversion log): its sound is then not validated. The report (`liveness`) records, per route, how many different pictures,
  audio blocks, RAM states and program counters the delivered file went through: it shows that picture and sound
  change, not how deep into the game the routes reach.
- **CPU and hardware checks:** authored video, audio, timing, session and disk vectors (`tools/x68000_*_check.py`) and
  the 20 authored CPU guards; independent CPU and hardware evidence are partial in QUALIFICATION.md.
- **Reference games:** R-Type (Irem) is the release-check game. Risk cases (`tools/campaign-risk-cases.json`): R-Type
  (single disk, control), Metal Sight (five-disk set, disk changes), Lemmings (mouse, drives the SCC channel itself),
  Super Hang-On (two disks, ejects after loading, must run as without the policy).
- **Mouse list:** 84 reviewed sets ([Mouse games](#mouse-games)).

## 8. Known limits

- **Not claimed:** complete gameplay coverage, exact hardware fidelity, physical latency. Interpreter fallback is
  counted and shown, and the conversion tries to reduce it.
- More games, disk sequences, hardware cases and low-power Linux performance still need qualification. Disk requests
  deeper than the conversion routes reach, and mouse use deeper than the mouse routes, are not observed.
- Floppy media only; no hard-disk or SCSI images.
- A few games (three or four known) play no sound on the machine as modelled, some because they play only through an
  external Roland MIDI module, which will not be modelled. Since 1.6.5 such a route is accepted and reported as silent
  instead of refused (decided on 29 October 2026, for the X68000 only): Pensan CD runs and shows its title screen, programs
  the FM chip but never keys a note on, and uses no ADPCM or MIDI in 4,000 frames.
- Quick states are refused between releases; exports are converted in full once per release.
- One px68k-libretro fix is not adopted ([UPSTREAMS.md](UPSTREAMS.md)): paired-bit OR in the graphic layer and the text
  transparency test at one priority, for lack of a game or a document to settle the behaviour.
- Improve the machine-runtime distribution boundary and extend multi-disk coverage. More consoles and classic
  computers are planned; each new machine gets its own experimental stage and validation before being described as
  supported, and no release dates or complete compatibility are promised.

  A crash of the frame loop when a game reprograms the CRTC during a line (Tetris v5, TF4G v0.3A09) is fixed
  ([UPGRADES.md](UPGRADES.md#x68000-a-picture-line-made-visible-during-its-machine-line-165)).
